# 内容筛选、反馈与检索迭代设计

日期：2026-09-29。状态：实施中，人工验收与运行接入未完成。

有效本地入口见[操作指南](../content-iteration-guide.md)，实测与缺口见[实施记录](../process/content-iteration-2026-09-29.md)。

目标是减少重复阅读、提高内容找回率，并用明确反馈检验筛选质量。
方案沿用现有 Python、SQLite/JSONL、Telegram 和 Mac/r4s 分工。
本文定义拟新增的行为与验收条件；当前实现以表内代码符号为准，部署状态由运行回执确认。

## 范围与顺序

| 阶段 | 交付重点 | 前置条件 |
| --- | --- | --- |
| P0 | 精选离线回放、反馈入口、健康与未知投递复核清单 | 固定真实样本及来源引用 |
| P1 | 价值排序对比、rubric 候选回归、关注事件档案、调用响应复用 | P0 能稳定关联内容与反馈 |
| P2 | 知识检索用户入口、来源质量复盘 | 对应检索发布条件通过 |

每个阶段独立验收。反馈、档案、评测和调用记录均作为旁路能力，失败时保留现有正文投递。
首版不建设公众网站、多用户账户或热度排行榜，也不迁移现有存储。
运行机器、代理和状态写入要求沿用 [AGENTS.md](../../AGENTS.md)。
`docs/rewrite/` 保存独立重写方案的冻结规格，本设计采用现有代码上的增量迭代。
本迭代涉及预算机制等差异时，以本文当前决定及对应有效指南为准；冻结规格保持原样。
去重的有效规则与发布条件集中在 [去重策略](../dedup-policy.md) 和

## P0：精选回放与反馈入口

### 固定回放数据

首版选取 30 条有完整原文的真实内容，覆盖微信、Telegram、媒体摘要和成长卡片。
包含明确有用、无用、同事件重复、实质进展以及难判断的样本。
这些数量是首版采样目标；样本不足时报告实际构成，不用合成记录补齐真人判断。

每条样本保留 `sample_id`、`content_id`、来源引用、正文 hash、采集时间、候选输出、
人工标签和标注理由。原文保持不变，后续更正产生新版本并记录关系。
人工标签至少区分“值得推”“可省略”“暂无法判断”。
模型分数与人工标签分列，历史 A/B 胜出结果仅作为模型评审结果。
先按事件和重复内容分组，再划分开发集与留出集，防止同一事件的转述落到两边。
开发集用于调整规则；留出集在候选规则冻结后使用，结果不满意时另起版本。
采样清单记录样本 hash、分组与划分版本，反馈仅用于抽样，不能自动变成人工标签。

回放只读取冻结样本，不发送 Telegram、不写 seen、不生成完成 marker。
运行输出记录规则版本、模型身份、输入 hash、判定、失败原因和处理耗时。
相同样本集同时运行当前规则与候选规则，报告全部分歧及原文入口。

### Telegram 操作

首版支持回复已投递消息的两种明确指令：“展开”和“少推这类”。
“展开”记录 `expand`；“少推这类”记录 `filter`，附上原始指令文本。
保留已有事件枚举，暂不增加“点赞”等含义不清的通用分数。

拟新增映射适配器以 `(chat_id, message_id)` 查询已确认回执：媒体记录走
`sent_ledger.lookup`，文本记录从 `sent-content.v1` 派生索引。
媒体 `id` 和文本 `content_id` 均为可选字段；缺失时由适配器依据 producer、可验证源引用和
内容版本建立稳定身份，保存映射来历。媒体账本本身不提供完整聊天原文引用。
首版只开放能唯一关联原文的媒体卡片和公开文本卡，日报分段与私有媒体待回执补齐后接入。
找不到唯一映射时进入 `needs_match`，保留原反馈等待补齐；不凭相邻消息或相似标题猜测。
多段正文与相册在适配器中归属于同一内容身份，同时保留各 Telegram message ID。

接收端核实并复用当前唯一消费者。成长入口支持 owner-filtered relay 或直接轮询，
实际运行分支以有效配置为准；现有私聊 relay 不能直接假定支持群内回复。
首版在同一消费者内增加 owner、目标 chat/topic 白名单校验，再路由回复事件。
外部群成员的回复不能更新个人偏好，不新增竞争 `getUpdates` 消费者。
消费 offset 只在入口事件持久化后推进；入口重试状态写入独立操作表，重启后可续办。

反馈幂等键由 bot 身份和 update ID 生成，重复交付只产生一条逻辑事件。
一条“少推”先进入每周偏好候选，保留适用主题及来源；不自动永久关闭整个信源。
“展开”的内容来自关联原文，并继续带原文链接。
展开失败返回具体原因，原始推送保持可读。

拟新增的入口处理状态为 `received → matched → recorded → responded`。
无法匹配停在 `needs_match`，处理失败记 `failed`，重试使用原幂等键。
回复发送结果未知记 `response_unknown`，进入投递复核，不盲目重发。
`recorded` 表示反馈写入成功；只有明确收到回复发送回执才记 `responded`。
已有 `FeedbackStore` 事件 schema 不承担入口重试状态；入口操作表是处理回执，保留失败历史。

### 验收

- 每条回放结果能定位到原文、规则版本和人工标签。
- 同一输入运行两次不会增加反馈或人工标注记录。
- 重复消息、相册、分段正文、无映射消息、非 owner 指令和错误目标都有用例覆盖。
- 标注报告给出值得推内容的保留率、可省略内容的放行率及对应分母。
- 试用记录明确指令数、成功匹配数、展开成功数；发送成功不计为已读。
- P0 不改变去重抑制开关或内容阈值。

## P1：价值排序对比

以有原文依据的候选条目为单位，新增仅记录的 `value_profile`：内容类型、与关注任务的
相关性、信息增量、证据质量和可用性，每项附具体来源引用及可判定状态。
原文不足时标记缺失；不要求模型补全事实或给出看似精确的分数。
提示词版本、字段 schema 和合成排序规则都纳入回放身份，结构错误保留原排序。

工具与实操内容侧重适用条件和能否操作，研究与新闻侧重事实依据和新增信息。
各类型的排序规则先写成可比较的候选版本，程序校验字段并合成排序。
全量候选先保持现有输出，只有临界项或版本分歧项进行第二次评审。
初期不把 LLM 总分直接用于拦截消息，也不调整既有 vision 阈值。

验收在相同候选池内比较两组各 10 条的列表，隐藏版本名后人工选择。
报告有用条数、必读漏选、类型覆盖、阅读耗时和额外模型调用数。
采样数量、严重漏选的定义和候选采用条件在跑留出集前固定；保留全部失败结果。
先在本地日报预览中试用，选用候选排序与开启去重抑制分别决定。

## P1：rubric 候选回归

`merge_rubric` 目前会保存旧版本并写入新版规则。
拟将更新流程拆为候选生成、固定样本回放、分歧复审和显式切换。
现有 rubric 持续服务在线任务，候选规则单独保存。

候选记录包含父版本、反馈事件 ID、生成时间、规则正文 hash 和变更理由。
使用 P0 的成长样本子集进行回归；不足 20 条时，补充真实历史卡片后再比较。
除内容偏好外，还标注是否过长、是否丢失原意、是否夸大结论。

每次复审优先展示最多 5 条影响最大的分歧，并保留完整分歧文件。
“影响最大”按人工标签由值得推变为省略、原意损失、其余分歧排序。
无法自动确定严重程度时列为待复审，不让模型自行批准候选。

候选状态为 `draft → evaluated → reviewed → active`，被拒版本进入 `rejected`。
只有带人工决定、对应评测 ID 和父版本检查的切换动作能更新 active。
父版本已经变化时重新回归，避免旧候选覆盖新偏好。
切换保留回滚指针，周报引用版本差异和样本结果，不重述完整 rubric。

首版交付候选生成命令、回放报告和切换/回滚命令。
验收要求规则版本可追溯，空输出、格式损坏、回放失败均保留原版本。
真人标为“值得推”的内容若被新规则省略，必须在复审结果中逐条解释。
是否采用候选由完整结果决定，不设未经校准的统一准确率门槛。

## P1：关注事件与来源独立性

先为明确标记“关注”的 3–5 个事件生成 Markdown 档案。
每份档案包含当前已知事实、本次新增、按时间排列的来源、冲突和更正记录。
沿用 `SameEventJudge` 的候选判断，事件档案与线上去重决策分开落盘。
原消息按现有链路处理；档案生成失败不改变投递结果。

### 关联与更新

候选输入携带 `content_id`、既有事件 ID、来源、发布时间和判定理由。
“同一主题”和“同一事件”分开记录；同主题新事件保留独立身份。
首版关联状态为 `proposed → confirmed` 或 `rejected`，人工可纠正归属。
确认过的人工归属不会被定时刷新覆盖。

综述版本绑定参与的原文 ID 与正文 hash。
新输入只在新增事实、冲突或更正时形成进展项；标题改写不算新增事实。
原文被更正时从有效原文重新生成当前综述，旧版保留在历史目录。
档案状态使用 `following`、`paused`、`closed`，由明确操作控制。
长期无更新只标出最后更新时间，不自动取消关注。

### 来源独立性

为每条来源保存发布者、原始链接、引用对象及可确认的上游出处。
同一官方公告的转载共享出处组；无法确认上游时标记 `unknown`。
首版只采用明确链接和人工核实的归并关系，模型建议先进入待复审列表。
统计同时显示发布渠道数和已确认独立出处数，未知项单列。

独立出处数量用于理解证据构成，不直接决定个人推送优先级。
一手来源、复述、评论分别展示；观点不同不能自动证明来源独立。
来源质量周报将采集成功率、内容有用率和来源独立性分列，避免混成单一分数。

验收使用人工确认的同事件、同主题异事件、同稿转载和实质进展样本。
报告错误合并、错误拆分、漏掉进展的条数与原文。
每份档案的新增事实必须能找到具体来源，且支持撤销错误归属后重建。

## P0：健康汇总与未知投递复核

健康汇总面向采集和投递运行状态，包括信源抓取失败、连续空结果、队列停滞、
模型降级、未知投递以及恢复情况。优先读取现有日志、incident 和 ledger。
每项发现带机器、生产者、首次/最近发生时间、影响范围和下一步操作。
成功抓取时间与最新内容时间分列，区分故障、确实无更新和解析后为空；
来源耗时日志仅表示任务结束时，不能据此认定抓取成功。
Mac 与 r4s 分别提供本机事实，再由汇总端关联，不从同步副本推断远端服务健康。

`AmbiguousDeliveryError` 已处理发送结果未知的情况；成长存储已有 `mark_ambiguous`。
拟增加统一复核清单，保留内容身份、请求时间、目标引用、transport 错误和已知回执。
清单不写密钥或完整带凭据的 endpoint，日志脱敏沿用
[logging_setup.py](../../src/chat_daily_tg/logging_setup.py) 的 `redact`。

复核状态为 `unknown → confirmed_sent` 或 `confirmed_absent`。
确认已送达需要实际 Telegram 消息引用；确认未送达需要记录核对范围与操作者。
只有 `confirmed_absent` 才可由明确重发动作进入 `retry_requested`。
重发产生新 attempt，沿用逻辑内容 ID，成功后按原链路更新状态。
证据不足保持 unknown，超时本身不触发非幂等自动重发。

首版先产出本地每日复核文件；发送健康汇总通过独立的现有通知配置接入。
同一问题未变化时合并次数，恢复形成独立记录，避免每次巡检重复通知。
验收覆盖成功回执丢失、发送前失败、部分相册成功和人工核对仍无结论。
指标是待复核年龄、已解决条目数、重复发送条数及每个结论的证据完整性。

## P1：无预算限额的调用记录与响应复用

本迭代移除 Jev 专项的单轮/每日预算预留及 shadow 同类实现。
保留通用 L2 的 `max_judge_calls_per_run`，它限制单轮判定工作量，也适用于原 LLM。
两者的有效范围见 [Jev 指南](../jev-dedup.md)，不将预算移除解释为无限调用。
调用记录用于定位问题、比较响应和复用结果，不作为预算熔断输入。
保留单次超时、有界重试、限流处理、响应校验、fallback 和 report-only 发布门控。
具体网络参数引用 `JevClient`，不在此维护另一套默认值。

首版回执保存逻辑请求 ID、attempt ID、阶段、模型身份、输入 hash、问题 schema hash、
提示词/策略版本、开始时间、耗时、usage、状态、错误分类与 provider request ID。
字段不可用时留空并说明原因；本地 attempt 身份始终生成。
原始响应保存在受限运行目录，进入回放数据前脱敏；摘要日志只保存引用和校验值。

响应复用键至少包含服务/模型标识、输入、问题定义和解释响应所需的策略版本。
只有通过 schema 校验且已持久化的成功响应可命中缓存。
如果模型别名不能确定实际版本，设置短有效期或显式禁用跨运行复用。
重新评测要求新响应时支持绕过复用，并记录 `origin=live`。
命中复用记录 `origin=reused` 及原回执 ID，不伪造本次网络调用或 usage。

请求状态为 `started → succeeded`、`failed` 或 `unknown`。
unknown 表示本地未取得可靠终态，不进入成功缓存。
调用超时是否再次尝试沿用各 client 的明确策略；到达本次重试边界后执行既有回退。
缓存、回执写入失败均不得阻断正文投递，也不得将失败响应当成终态抑制依据。

交付包含回执 writer、成功响应 reader 和有版本的 cache key。
验收覆盖输入/schema/版本变化失效、失败不复用、并发同键以及存储故障降级。
报告实际网络尝试数、成功复用数、失败类型和耗时；这些是观测值，不是调用配额。

## P2：现有知识检索的使用入口

检索实现和发布过程沿用 [KnowledgeIndex 操作指南](../knowledge-index-runbook.md)。
满足发布条件前仅运行 `diagnostic-query`，不把旁路 generation 接成正式入口。
正式入口继续通过 `_require_knowledge_retrieval` 检查，并保留降级和回滚。

先提供两个任务：“找以前看过的 X”和“最近一周 X 有什么进展”。
首个任务默认查已有可靠消费事件；没有消费事件时明确展示为已投递内容。
不能将 `read` 以外的反馈、发送回执或展开请求推断成阅读完成。
第二个任务查询限定时间的材料，并在存在已确认事件档案时给出对应入口。

每次返回最多 3 条结果，包含标题、日期、原文链接、匹配片段与查询范围。
零结果可显式扩大到可用归档，响应说明扩大后的来源和时间范围。
首版使用 CLI/Agent 工具封装，Telegram 查询入口在实际使用频率明确后再接入。
使用 20 条真实个人找回问题检验 top-3 命中率、原文可达率和找回耗时。
这组产品体验样本单独记录，不替代现有检索发布评测要求。

## 数据流与交付边界

原文进入既有采集、筛选、投递链路，成功回执连接 `content_id` 和目标消息。
反馈入口从目标消息查回内容，追加意图事件；事件为评测和候选规则提供输入。
固定样本产生回放报告，人工复审决定 rubric 切换和事件归属。
确认后的事件档案、健康视图和知识索引均由原始记录重建。
调用回执记录各步实际执行情况，成功响应复用不改变业务状态的写入顺序。

每项交付同时记录代码版本、样本版本、命令、实际结果和失败记录。
本地验证、目标机器运行、真实 Telegram 回执分别列出。
部署前核对对应机器的配置与在途任务；本文不指定或更改线上 schedule。
验收产物使用带日期目录，长期指南只保留查询方法和有效操作。
后续实施完成后，将有效用法写入对应指南，并在本文标注实施版本及验收报告链接。
