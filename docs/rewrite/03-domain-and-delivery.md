# 领域与投递状态

本文件规定身份、状态及恢复语义。名字可在实现中调整，但各概念不能合并成一个布尔标记。

## 核心对象

| 对象 | 必须表达的事实 |
|---|---|
| Source | 平台、账户/空间、稳定来源 ID、展示名、访问范围 |
| SourceItem | 来源身份、平台 item ID、源时间/采集时间、正文与附件、原始引用、修订/删除状态 |
| SourceBatch | 时间/游标覆盖范围、完整性、分页与失败区间、采集版本 |
| ContentRevision | 逻辑内容身份、输入引用、正文 hash、生成版本、模型/策略版本、归档定位 |
| RouteRevision | 业务路由键、实际 chat/topic、Bot 身份引用、fallback 与配置版本 |
| DeliveryPlan | 内容版本、目标快照、有序的必需/可选部件、幂等范围 |
| DeliveryAttempt | 部件、尝试序号、领取权、发起/结束时间、传输结果、回执或待核验信息 |
| Decision | 过滤/去重依据、规则版本、候选引用、请求/有效模式、人工判定 |
| Run | 管线、业务窗口、触发、配置、来源覆盖、阶段结果与关联投递 |
| FeedbackEvent | 事件身份、操作者、内容引用、意图、来源与处理状态 |
| IndexGeneration | 原文版本集合、模型/维度/分块版本、评测与发布状态 |

来源身份至少包含 `(平台, 账户或命名空间, 来源ID, itemID)`。媒体成员有各自身份。内容指纹用于查重，不取代源身份。Telegram 目标 message ID 在 chat 内唯一，不能只存裸 message ID。

自动投递的幂等范围包含订阅/投递目的、逻辑源或报告周期、目标业务键与内容版本。**内容重新生成不会自动创建第二次正式投递**：已完成的日报业务周期首先命中周期级完成记录；只有显式的更正/补发命令才能创建新版本投递。新增目标由配置决定仅处理未来内容还是显式回放，默认不回放历史。

## 三种执行模式

| 模式 | 外部读取 | 模型调用 | 业务状态与归档 | 外部发送 |
|---|---|---|---|---|
| 只读检查/预览 | 仅已声明只读查询 | 默认不调用 | 不改变游标、反馈、配额、规则或投递状态；可写隔离的诊断输出 | 无 |
| 生成但不发送 | 可以 | 按预算 | 可以写独立草稿与归档，明确声明副作用；不推进送达状态 | 无，包括业务告警 |
| 正式运行 | 可以 | 按预算 | 按合同提交 | 发往冻结的目标 |

历史回放另建命名空间，默认使用模拟发送；若要真实重投，须显式选定来源范围和目标。内部模式不能靠同一个含混的 `dry-run` 开关兼任。

## 投递状态

| 状态 | 含义 | 自动动作 |
|---|---|---|
| pending | 有待处理输入或投递计划 | 调度处理 |
| preparing | 正在生成/校验正文与计划 | 有界恢复 |
| ready | 计划固定，满足发送条件 | 可领取 |
| sending | 当前尝试可能已到达外部系统 | 不允许第二执行者重发 |
| confirmed | 有成功响应回执，或可靠读回/人工核验绑定的回执 | 常规重跑不重发 |
| failed_retryable | 能确认该尝试未产生外部副作用，且重试仍有意义 | 有界重试 |
| failed_terminal | 该尝试无法自动恢复，例如目标权限或配置错误且重试无益 | 告警、修复后显式恢复 |
| ambiguous | 请求可能成功，本地不能确认 | 进入待核验，不自动重 POST |
| suppressed | 可审计规则决定不发 | 保留来源和决定，允许人工恢复 |
| cancelled | 发送前取消，未执行部分不再自动发送 | 已发送部分保持原状态 |

`degraded` 是质量标志，例如正文已发但图片缺失；它不能覆盖 confirmed/ambiguous 等传输状态。发送成功后的派生索引或 ledger 失败，记录 `repair_pending`，与真实送达分开。

### 状态提交规则

1. 抓取完成只表示输入已覆盖；它不代表正文生成或投递完成。
2. 先保存可重放输入再推进抓取游标；未保存或未覆盖区间留作空洞。更高 ID 的成功不能跳过低 ID 的失败。
3. 规则终态必须与 Decision 一致持久化。决定无法记录时，该规则退出抑制路径。
4. 发送前固定内容、部件顺序与目标，领取具有 owner、到期和 fencing 标识；过期领取不能让旧执行者继续提交。单写者还必须在发送出口或旧执行环境隔离，不能仅靠数据库拒绝提交阻挡一个仍持有 Bot token 的旧进程。切主采用具备所有权校验的统一发送入口、停止并隔离旧执行环境、限制旧出口等可验证方案之一。已进入 sending 的遗留尝试先核验，不能直接转 ready。
5. 发送回执至少含目标、message IDs、时间和尝试关联。原始响应须脱敏保存或记录可核验摘要。
6. 所有必需内容义务由其允许的一个交付分支 confirmed 后，才算主内容完成；可选图片失败不重发正文。含 ambiguous 必需部件的 run 为待确认，不能写完成标记。
7. 同一业务周期已完成时，普通重跑直接返回结果，不重新消耗反馈、配额或模型预算。

### 为什么不能承诺绝对不重不漏

[Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage) 成功会返回 Message，其请求合同没有应用自定义的通用幂等键。外部发送与本地提交无法合并为一个事务。因此“服务端成功但回执丢失”要以 ambiguous 保存，结合读回或人工复核处理，而不是把超时统一重试。

## 分块、相册与修订

投递计划在发送前确定内容义务、部件 ID、序号、类型、正文 hash、必需性及允许的替代分支。媒体明确失败时，可用预先允许的文字/来源占位分支满足同一内容义务，记录 replaces/satisfies 关联；失败的媒体 attempt 保持失败，不能伪标 confirmed。替代分支成功后无需再发正文，媒体完整性仍标 degraded。原分支 ambiguous 时禁止自动走替代分支。文本第 1/3 部分确认、第 2/3 部分明确失败时，只恢复第 2、3 部分；第 2 部分 ambiguous 时停止后续依赖部件，先核验。所有历史部件回执一直可查。

相册同时保留源成员集合和目标消息集合；媒体与 caption 分开发送也使用同一计划。上游删除某个附件时记录缺口，按已声明的降级方式交付。正文变化创建 revision；尚无任何外部尝试的计划可原子取消并改建新计划。任一部件进入 sending 后，旧计划保持固定，编辑只能形成独立修订，通过显式更正或取消未发部件处理；不能把已发首段与新正文尾段拼在一起。

## 正文优先与存储故障

派生 Markdown/卡片导出、机会视图、检索索引、图片、评审模型和兼容 ledger 均为可恢复增强，失败不能挡住有效正文。可重放输入与来源覆盖证据是核心事实，必须持久化后才能推进采集游标，不能归入可丢弃的归档增强。核心投递记录也要有有界故障策略：先尝试独立的紧急持久日志，再在恢复后合并回主存储。

主存储与紧急日志同时不可写时，继续发送会失去跨进程去重凭据，暂停则会延迟正文。这个取舍在 [D01](10-decisions.md#d01) 单独决定，不能把“正文优先”解释成已实现完整可恢复性，也不能未经决定把旧部署改成一遇存储故障便停发。开发故障用例要支持观察两种策略的结果。

## 汇总状态与配额

日报、成长日卡、周报、订阅均区分无内容、规则过滤、部分来源失败、主内容送达、发送待确认。run 汇总不得掩盖必需部件的异常。

日配额按配置时区、业务卡/逻辑投递义务计数，一张卡拆多段仍算一张。发送前原子预留，两个 worker 不能同时占用最后一个额度；confirmed 结算，ambiguous 保留预留直到核验，确认未发的失败释放，suppressed 不算已送达。同一计划的恢复不再占额度；显式新补发默认作为新投递计数，若人工豁免必须记录理由。

周期处理结论与送达结论分开：完整覆盖且无内容时，可结束该次处理并避免重复调用模型，但不生成送达结果。有缺口时继续补采；如果日报主文已发，迟到材料默认入归档并提示差异，不自动重发日报。

## 人工恢复

核验操作可将 ambiguous 关联到确认存在的目标回执，或证明未发送后释放为可恢复。人工确认必须记录操作者、理由与证据；查询不到并不天然证明未发送。明确无法查证时允许人工选择“继续保留待确认”或“承担可能重复的补发”，后者创建新 attempt 并保留原歧义。

普通路由修改不改在途目标快照；安全或隐私授权被撤销时，发送边界重新检查授权，取消或暂停尚未发出的部件，不自动转投另一个目标。已被平台接受的请求不能靠本地取消撤回，保留其实际结果。

人工推翻 suppressed 时创建恢复命令，原判定不删除。一般重试、强制补发、重新生成、更正消息是不同操作，界面与 CLI 必须分别命名。
